## ⚠️ БЛОК 1. Rate limits — главный вывод

> **В официальной документации Fleet API НЕТ ни одного конкретного числа по
> частоте запросов.** Ни RPS, ни RPM, ни суточной квоты, ни размера
> «ведра» (burst), ни заголовков `X-RateLimit-*`, ни `Retry-After`.

Единственное, что документировано про лимиты — одна строка в таблице кодов
ответа на странице «Взаимодействие»:

| Код | Причина | Описание |
|-----|---------|----------|
| 429 | TooManyRequests | Превышены ограничения |

Проверено дословно: на странице «Взаимодействие» отсутствуют слова
«лимит», «частота», «Retry-After», «идемпотентность», а также любые
упоминания часовых поясов и форматов дат. Слово «ограничения» встречается
ровно один раз — в описании кода 429.

### Что это означает для опроса раз в минуту

1. **Порог неизвестен и не зафиксирован контрактом.** Яндекс может менять его
   без изменения документации. Проектировать нужно так, чтобы система
   выдерживала 429 в любой момент, а не «укладывалась в известное число».
2. **Поведение при превышении не описано.** Документация не обещает
   `Retry-After`, не описывает окно сброса и не говорит, блокируется ли ключ
   при систематическом превышении. Считать `Retry-After` отсутствующим и
   опираться на собственный экспоненциальный backoff.
3. **Практическая рекомендация для проектирования:**
   - клиентский троттлинг на своей стороне (token bucket), а не «шлём и
     ловим 429»;
   - на 429 — экспоненциальный backoff с джиттером, начиная с 1–2 с,
     потолок 60 с;
   - если ответ всё-таки содержит `Retry-After` — уважать его приоритетно;
   - глобальный circuit breaker на весь пул воркеров парка: 429 приходит на
     ключ/клиента, а не на конкретный воркер, поэтому пятиться должны все;
   - точный порог выяснять эмпирически (наращивать нагрузку и фиксировать,
     на какой скорости появляется 429) и/или письмом в
     <api-taxi@yandex-team.ru>.
4. **Бюджет запросов на минуту считать через пагинацию** (см. блок 4):
   при 1000 машин/водителей за запрос полный проход по парку — это единицы
   запросов, а не сотни. Опасны не сами циклы опроса, а параллельные
   пообъектные запросы (профиль/баланс/трек по каждому водителю).

## БЛОК 2. Введение

> «В документе описан API Яндекс.Такси для партнеров сервиса (далее — API
> Такси, API).»

Назначение — встроить возможности партнёрского интерфейса (Диспетчерской) в
собственную систему. Заявленные возможности:

- выгрузка информации для построения собственных отчётов;
- проведение выплат и списаний со счёта водителя;
- изменение связи водителя с автомобилем.

Разделы документации: Введение, Авторизация, Взаимодействие, Ресурсы API.
Контакт для вопросов: <api-taxi@yandex-team.ru>.

## БЛОК 3. Авторизация

### Что нужно

> «Для авторизации запросов необходимы:
> Идентификатор партнера **park_id**.
> Идентификатор клиента **X-Client-ID**.
> Секретный API-ключ **X-API-Key**.»

### Куда что кладётся

| Что | Где передаётся | Назначение |
|-----|----------------|------------|
| `X-Client-ID` | HTTP-заголовок | Идентификатор клиента |
| `X-API-Key` | HTTP-заголовок | Секретный API-ключ |
| `park_id` | **тело запроса** (JSON) или query-параметр метода — не заголовок | Идентификатор партнёра (парка) |

Важно: `park_id` **не** является заголовком. В POST-методах он лежит внутри
JSON-тела (например `query.park.id`), в GET-методах — в query-строке.
Отдельного заголовка `X-Park-ID` в документации нет.

Регистр в примерах Яндекса непоследователен: в таблице заголовков указан
`X-API-Key`, в curl-примере — `X-Api-Key`. HTTP-заголовки регистронезависимы,
так что подойдёт любой вариант.

### Как получить ключ

> «Чтобы получить их выберете в Диспетчерской пункт «Настройки» и перейдите
> в раздел API. Редактировать его может только сотрудник с ролью
> «Директор».»

То есть: Диспетчерская → Настройки → API. Права на редактирование — только у
роли «Директор». Ротация ключа делается там же вручную; программного метода
выпуска/обновления ключа в API нет.

### Пример запроса (дословно из документации)

```bash
curl -X POST \
  https://fleet-api.taxi.yandex.net/v1/parks/driver-profiles/list \
  -H 'X-Client-ID: <Идентификатор клиента>' \
  -H 'X-Api-Key: <Секретный API-ключ>' \
  -d '{
 "query": {
  "park": {
   "id": "<Идентификатор партнера>"
  }
 }
}'
```

### Ошибки авторизации

Отдельного раздела с кодами ошибок авторизации нет. Из общей таблицы кодов:

- `401 Unauthorized` — «Отсутствуют параметры авторизации» (нет/некорректны
  заголовки);
- `403 Forbidden` — «Не достаточно прав для выполнения запроса» (ключ валиден,
  но нет доступа к ресурсу или к этому `park_id`).

## БЛОК 4. Взаимодействие

### Транспорт и формат

> «Взаимодействие с API осуществляется по адресу:
> `https://fleet-api.taxi.yandex.net`»

- Канал передачи данных — защищённый протокол **HTTPS**.
- Для представления данных в теле запроса и ответа используется формат
  **JSON**.
- Версия метода зашита в путь (`/v1/...`, `/v2/...`, `/v3/...`); единого
  общего версионирования API нет — версии живут на уровне отдельных методов,
  и одновременно существуют разные версии одного и того же ресурса.
- Выборки списков — почти везде **POST** с JSON-телом, а не GET.

### Заголовки запроса

Общие заголовки для запросов в API:

| Заголовок | Описание |
|-----------|----------|
| `X-Client-ID` | Идентификатор клиента |
| `X-API-Key` | Секретный API-ключ |
| `Accept-Language` | Язык ответа (по умолчанию `en`) |

Для русскоязычных ответов и текстов ошибок нужно явно слать
`Accept-Language: ru`, иначе придёт английский.

### Коды ответа

| Код | Причина | Описание |
|-----|---------|----------|
| 200 | OK | Запрос выполнен успешно |
| 400 | BadRequest | Некорректные параметры запроса |
| 401 | Unauthorized | Отсутствуют параметры авторизации |
| 403 | Forbidden | Не достаточно прав для выполнения запроса |
| 404 | NotFound | Ресурс не найден |
| 409 | Conflict | Операция не может быть выполнена из-за конфликта изменений |
| 429 | TooManyRequests | Превышены ограничения |
| 500 | InternalServerError | Внутренняя ошибка сервера |

### Формат ошибок

Формат неуспешных ответов на запрос:

```json
{
    "code": "необязательное поле с машиночитаемым кодом ошибки",
    "message": "обязательное поле с человекочитаемым сообщением об ошибке"
}
```

- `code` — **необязательное** поле с машиночитаемым кодом ошибки.
  Полагаться на его наличие нельзя.
- `message` — **обязательное** поле с человекочитаемым сообщением.
  Текст зависит от `Accept-Language`, поэтому парсить его нельзя — только
  логировать.

Практический вывод: единственный надёжный дискриминатор ошибки — HTTP-статус.

Вопросы по API: <api-taxi@yandex-team.ru>.

## БЛОК 5. Даты и часовые пояса

В общих разделах документации правил по датам **нет** — они заданы только в
схемах конкретных методов. Фактический контракт:

- Формат — **ISO 8601 с явным указанием временной зоны**.
- Дословная формулировка в схемах: «ISO 8601 с временной зоной».
- Пример из документации: `2019-08-08T11:58:01+03:00`.

Следствия для проектирования:

- смещение указывать обязательно; не полагаться на «серверный» пояс по
  умолчанию, поскольку он нигде не задокументирован;
- безопаснее всего слать и хранить UTC (`...Z` / `+00:00`), а в отображение
  переводить на своей стороне;
- в ответах смещение может приходить не в UTC (обычно `+03:00`, Москва) —
  парсер должен уметь читать любое смещение, а не только `Z`.

## БЛОК 6. Пагинация и ограничения на объём выборки

Общего раздела про пагинацию в документации нет. Схема зависит от метода —
их **две**, и они несовместимы.

### Схема A — курсорная (`cursor`)

Применяется в списках заказов и транзакций.

- Параметр `cursor` — «Курсор для получения следующий порции данных, значение
  должно быть взято из ответа на предыдущий запрос».
- Курсор — непрозрачная строка: не разбирать, не конструировать, передавать
  как есть.
- Признак конца выборки — отсутствие `cursor` в ответе.
- Поля `total` в курсорных методах нет: заранее узнать объём выборки нельзя.
- При передаче `cursor` остальные фильтры менять нельзя — курсор относится к
  зафиксированному запросу.

Конкретные лимиты:

| Метод | Параметр | По умолчанию | Min | Max |
|-------|----------|--------------|-----|-----|
| `POST /v1/parks/orders/list` — список заказов | `limit` | — | 1 | **500** |
| `POST /v2/parks/transactions/list` — транзакции по парку | `limit` | **40** | 1 | **1000** |

Для списка заказов также действует требование: «Обязательно наличие одного из
`booked_at` или `ended_at`» — то есть фильтр по периоду обязателен.
Максимальная ширина периода в документации не оговорена.

### Схема B — offset/limit

Применяется в справочных списках (водители, автомобили).

| Метод | `limit` (default / min / max) | `offset` (default / min) | `total` в ответе |
|-------|------------------------------|--------------------------|------------------|
| `POST /v1/parks/driver-profiles/list` | 1000 / 1 / **1000** | 0 / 0 | да — «Общее количество элементов списка» |
| `POST /v1/parks/cars/list` | 1000 / 1 / **1000** | 0 / 0 | да — «общее число автомобилей, удовлетворяющих запросу», min `0` |

Здесь `total` есть, поэтому число страниц считается заранее:
`ceil(total / limit)`.

### Сводка ограничений на объём

- Максимум за один запрос: **500** (заказы), **1000** (транзакции, водители,
  автомобили).
- Явного лимита на общее число страниц или на суммарный объём выгрузки в
  документации нет — фактическим ограничителем выступает недокументированный
  rate limit (см. блок 1).
- offset-пагинация нестабильна при изменяющихся данных: строка может
  задвоиться или потеряться между страницами. Для регулярного опроса
  предпочитать курсорные методы там, где они есть, и инкрементальные фильтры
  по времени там, где их нет.

## БЛОК 7. Чего в документации нет (важно знать заранее)

Перечисленное ниже **отсутствует** в общих разделах и должно закладываться в
проект как неопределённость:

- любые числовые rate limits, квоты, burst-ёмкость;
- заголовки `Retry-After` и `X-RateLimit-*`;
- описание поведения при систематическом превышении лимита (троттлинг vs
  блокировка ключа);
- идемпотентность и ключи идемпотентности для пишущих операций
  (создание транзакций) — на уровне общих правил не описана;
- вебхуки / push-уведомления: их нет, модель взаимодействия только
  pull (опрос);
- SLA, гарантии доступности, окна обслуживания;
- политика версионирования и депрекации (в списке ресурсов есть метод,
  прямо помеченный «Устаревший» — `POST /v2/parks/driver-profiles/transactions`,
  но правил вывода из эксплуатации не опубликовано);
- ограничение на максимальную ширину периода выборки.

## БЛОК 8. Карта ресурсов API (для ориентира)

Базовый адрес: `https://fleet-api.taxi.yandex.net`

- **Cars** — `POST/PUT/GET /v2/parks/vehicles/car`,
  `POST /v1/parks/cars/list`
- **ContractorProfiles** — `POST /v1/parks/driver-profiles/list`,
  `PUT|DELETE /v1/parks/driver-profiles/car-bindings`,
  `GET|POST|PUT /v2/parks/contractors/driver-profile`,
  `GET /v2/parks/contractors/supply-hours`,
  `GET /v1/parks/contractors/blocked-balance`, и др.
- **DriverWorkRules** — `GET /v1/parks/driver-work-rules`
- **Orders** — `POST /v1/parks/orders/list`, `POST /v1/parks/orders/track`
- **Transactions** — `POST /v2/parks/transactions/list`,
  `POST /v2/parks/driver-profiles/transactions/list`,
  `POST /v2/parks/orders/transactions/list`,
  `POST /v2/parks/transactions/categories/list`,
  `POST /v3/parks/driver-profiles/transactions`,
  `GET /v3/parks/driver-profiles/transactions/status`
