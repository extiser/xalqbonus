## Главное для нашего проекта

**Гипотеза о массовом опросе подтверждена документацией.** У `POST /v1/parks/orders/list`
фильтр `driver_profile.id` опционален, обязателен только `park.id`; фильтровать
можно по `ended_at`, и одного из `booked_at`/`ended_at` достаточно; идентификатор
водителя присутствует в каждом объекте заказа (`orders[].driver_profile.id`).
`limit` до 500, пагинация курсором.

Осталось подтвердить на живом API — документация и реальность у Яндекса расходятся.
Это issue 02.

**Ограничений по частоте запросов в документации нет ни одного.** Ни RPS, ни RPM,
ни суточной квоты, ни `Retry-After`, ни заголовков `X-RateLimit-*`. Единственное
упоминание — строка `429 TooManyRequests` в таблице кодов ответа. Поведение при
превышении не описано.

Отсюда следствие: «лимит 5 000 запросов в час», от которого отталкивался старый бот,
взят не из документации. Настоящий порог неизвестен, выясняется эмпирически или
письмом в Яндекс. В системе закладывается собственный token bucket, экспоненциальный
backoff с джиттером и circuit breaker на ключ.

**Вебхуков нет.** Только опрос.

**Авторизация** — два заголовка, `X-Client-ID` и `X-API-Key`. `park_id` идёт
в теле запроса, а не заголовком. Для русских сообщений об ошибках нужен
`Accept-Language: ru`, по умолчанию английский.

**Даты** — ISO 8601 с обязательной временной зоной: `2019-08-08T11:58:01+03:00`.
