# Принципы: баллы

## Баллы живут на счетах, операция всегда двусторонняя

Баллы не появляются и не исчезают — они перемещаются между счетами. Счёт бывает
водительский (принадлежит человеку) и системный: `emission` — источник эмиссии,
`redemption` — погашение при обмене на товар, `raffle_bank` — банк розыгрышей,
куда уходит сгоревшее.

Каждая операция — перевод: списание с одного счёта и зачисление на другой, две
записи журнала с общим идентификатором перевода, суммой ровно ноль.

Почему так, а не «просто плюс баллов водителю»: у программы уже запланированы
сгорание и розыгрыш с банком, а банк платит призы. При одностороннем журнале
баллы приходят из ниоткуда и уходят в никуда, и сойтись такому журналу не с чем.
При двусторонней записи обязательства парка равны сумме водительских счетов,
и эта сумма сама сходится с эмиссией за вычетом погашения — без отдельной
аналитики и без веры в неё.

Побочный эффект, который дорогого стоит: объединение двойных учётных записей
становится обычным переводом между двумя водительскими счетами, а не
привилегированной правкой балансов.

## Баланс — производная, а не значение

Баланс водителя определяется журналом операций. Поле с текущим балансом
существует как кэш и обновляется только вместе с записью в журнал,
в одной транзакции.

**Прямое изменение баланса запрещено везде**, кроме сервиса, который пишет журнал.

Почему это принцип, а не деталь реализации: в старом проекте баланс правили
пять независимых мест, журнала не было, и на вопрос «откуда у водителя столько
баллов» ответить было нечем. Это же породило гонку между фоновыми задачами —
одна инкрементировала на стороне базы, другая писала прочитанное ранее значение,
и начисления затирались.

## Каждая операция идемпотентна

У операции есть ключ, по которому она однозначно опознаётся, и уникальное
ограничение в базе на этот ключ. Повторная попытка не создаёт вторую запись.

Схема ключей — контракт между задачами, поэтому фиксируется здесь:

| Операция | Ключ | Откуда → куда |
|---|---|---|
| перенос баланса при запуске журнала | `opening:<persons.id>` | `emission` → водитель |
| начисление за поездку | `trip:<trips.order_id>` | `emission` → водитель |
| приветственный бонус | `welcome:<persons.id>` | `emission` → водитель |
| списание при заказе | `order_spend:<заказ товара>` | водитель → `redemption` |
| возврат при отмене | `order_refund:<заказ товара>` | `redemption` → водитель |
| ручная правка | `manual:<uuid>` | `emission` → водитель или обратно |
| массовое начисление по кампании | `campaign:<slug>:<persons.id>` | `emission` → водитель |
| доначисление по перепроверке | `recon:<trips.order_id>` | `emission` → водитель |
| сгорание | `expire:<person_id>:<YYYY-MM>` | водитель → `raffle_bank` |
| объединение двойников | `merge:<source_person_id>` | водитель → водитель |
| выплата приза | `raffle:<raffle_id>:<person_id>` | `raffle_bank` → водитель |

**Ключи подписаны колонкой-источником намеренно.** Прежняя запись `trip:<trip_id>`
пришла из терминологии старой базы, где `Trips.trip_id` и был идентификатором
заказа Fleet API — тем самым полем, которое в схеме `xb` называется
`trips.order_id`. Смысл не менялся ни разу, расходились имена.

Отдельно про два разных «заказа»: у поездки это заказ такси из Fleet API,
у списания и возврата — заказ товара за баллы, наша собственная сущность.
Одно слово, разные вещи; таблица каталога появится своим этапом, и ключ
допишется точным именем колонки тогда же.

Ключ строится **только** от внешнего идентификатора заказа, никогда от `trips.id`:
наш uuid генерится при вставке, и повторный импорт той же поездки после удаления
строки дал бы новый ключ и второе начисление — то есть ключ идемпотентности
перестал бы быть идемпотентным ровно там, где он нужен.

**Новую схему ключа придумывать нельзя.** Нужна — сначала правка этой таблицы,
потом код.

### Массовые начисления — своя причина, а не ручная правка

Праздничные и акционные раздачи в этой программе не разовое событие, а обычай:
парк начисляет всем работающим по случаю — так было ко Дню независимости
28.08.2026, так будет и дальше. Поэтому у них своя причина операции —
`campaign`, — и она не совпадает ни с `manual`, ни с `welcome`.

Не `manual`: ручная правка — это одна операция по одному человеку, заведённая
оператором по конкретному поводу, и её ключ содержит `uuid`, не значащий ничего.
Раздача на три с лишним тысячи человек, помеченная так же, перестаёт отличаться
от трёх тысяч независимых решений оператора, и вопрос «сколько мы раздали
к празднику» теряет ответ.

Не `welcome`: приветственный бонус привязан к человеку и случается с ним один
раз, кампаний же с одним человеком случается много.

`slug` в ключе — короткое имя кампании, `independence-2026` и подобные. Из этого
следуют оба нужных свойства: повторный прогон раздачи не начисляет дважды,
а разные кампании не мешают друг другу и считаются по отдельности.

Одна кампания — это по переводу на каждого получателя, а не один перевод на всех:
журнал двусторонний, и зачисление идёт на конкретный счёт. Отдельной сущности
«кампания» в базе нет — пока `slug` в ключе отвечает на все вопросы, заводить
её незачем; понадобится отчёт — появится тогда же.

Что из этого следует бесплатно: воркеры можно запускать параллельно,
глобальный мьютекс не нужен, ретраи безопасны, окна опроса можно перекрывать,
повторное нажатие «отменить» не возвращает баллы дважды.

Три бага старого проекта закрываются этим одним решением — гонка за балансом,
двойной возврат при повторной отмене, повторное начисление при перекрытии окон.

## Инварианты

Их четыре, и каждый проверяется запросом:

1. Сумма двух записей одного перевода равна нулю
2. Сумма записей по счёту равна кэшу баланса этого счёта
3. Сумма записей по всем счётам равна нулю
4. Водительский счёт никогда не уходит в минус

Первый ловит битую вставку, второй — запись мимо сервиса, третий — потерянную
половину перевода, четвёртый — двойное списание при обмене.

Расхождение по второму означает, что кто-то пишет мимо журнала.

Проверяется регулярно. На переходный период, пока жив старый бот, расхождение
ожидаемо — сверка сообщает, но не исправляет.

## Начисление за поездки

Балл начисляется за завершённую поездку, один раз за поездку, навсегда.

Окно опроса внешнего API строится **по времени завершения** поездки,
а не по времени бронирования, и перекрывается с предыдущим. Это то место,
где старый проект терял пятую часть поездок — подробности в `analysis.md`.

Курс — 1 балл за поездку, независимо от суммы и длительности. Это продуктовое
решение, унаследованное как есть; пересмотр обсуждается в `../product/`.

## Исправление прошлого

Перепроверка работает в два шага и никогда не начисляет автоматически:
сначала отчёт о расхождениях, потом осознанное применение, с возможностью
выборки по водителю или периоду.

Балл, появившийся у водителя неожиданно — это разговор с диспетчерской,
которого можно избежать, просто не начисляя молча.
