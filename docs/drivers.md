# Принципы: водитель

## Три уровня личности, и их нельзя путать

Именно смешение этих уровней породило все известные проблемы старого проекта —
и восемь двойных учётных записей, и дыру с чужим контактом.

| уровень | ключ | меняется |
|---|---|---|
| **человек** | номер водительского удостоверения | практически никогда |
| **учётка в парке** | `profile_id` во внешнем API | при переоформлении в парке |
| **канал связи** | телефон, `chat_id` | часто |

**Баланс баллов принадлежит человеку**, а не учётке и не мессенджеру.
Из этого следует всё остальное:

- смена телефона не создаёт нового водителя, а обновляет контакт
- увольнение и возвращение — тот же человек, баллы находятся сами
- перепривязка Telegram не переносит баллы, потому что переносить нечего:
  меняется доступ, а не владелец

Старый бот считал личностью телефон — уникальность по нему, регистрация создаёт
водителя. Поэтому восемь водителей, сменивших номер, существуют в базе дважды,
с разделённым балансом и параллельными начислениями на обе записи.

## Реестр парка и участие в программе — разные вещи

**Реестр** приходит из внешнего API и содержит всех, кого знает парк, включая
уволенных и тех, кто никогда не открывал бота. Он нужен, чтобы видеть парк
целиком: кто есть, кто ушёл, кого можно вернуть.

**Участие в программе** начинается с привязки Telegram. Только у участников есть
баланс, уведомления и интерфейс.

Смешивать нельзя. В старом проекте водитель рождался в боте, поэтому база
знала только дошедших до регистрации — и размер парка был неизвестен в принципе.

## Привязка Telegram: автоматически или в офис

Бот **никогда не создаёт водителя**. Он связывает Telegram с записью, которая
уже есть в реестре.

**Автоматически — по телефону.** Telegram отдаёт подтверждённый номер владельца
аккаунта, внешний API отдаёт номера водителя списком. Совпадение ровно с одним
активным профилем, у которого нет привязанного Telegram, — привязываем молча.
Это большинство случаев.

**Всё остальное — в офис.** Номер не найден, совпал с несколькими профилями,
профиль уже привязан к другому Telegram — бот не устраивает допрос, а говорит,
куда прийти. Оператор видит водителя лично, с документами, и решает.

**Почему не «сверить побольше данных автоматически».** Всё, что водитель вводит
руками — номер удостоверения, номер машины — не является секретом: машину коллеги
видно каждый день, права водитель показывает. Автопривязка по введённым данным
воспроизвела бы старую дыру в новой форме. Подтверждённым является только телефон
из Telegram, поэтому автоматика строится на нём одном.

Экономии на этом нет: за проблемами водители и так приходят в офис, а ручная
проверка там уже работает. Задача системы — не заменить оператора, а дать ему
экран вместо тетради.

## Телефон подтверждает только сам владелец

**Контакт принимается, только если он принадлежит отправителю.**

В старом проекте телефон читался из присланного контакта без сверки с отправителем,
а кнопка «отправить контакт» — не единственный способ прислать контакт: через
скрепку прикладывается любой контакт из адресной книги. Дальше срабатывала ветка
«водитель найден по телефону — привязываем текущий чат», и аккаунт чужого водителя
переезжал на отправителя вместе со всеми баллами.

Для этого достаточно знать номер телефона коллеги.

## Смена номера чинится в парке, а не у нас

Основной путь при смене телефона — водитель сообщает новый номер в офисе, номер
обновляется **во внешнем API**, и на следующей синхронизации всё сходится само.

Мы не заводим собственного места, где номер можно поменять мимо парка: два
источника истины по контактам разъедутся так же, как разъехались балансы.

## Перепривязка — операция, а не побочный эффект

Смена Telegram у существующего водителя никогда не происходит молча внутри
регистрации. Это отдельное действие: выполняет оператор, с записью в журнал,
с уведомлением на прежний чат, с возможностью потом разобраться, кто и когда.

Автоматических перепривязок не бывает ни при каких совпадениях.

## Статус трудоустройства ведём сами

Внешний API отдаёт текущий статус водителя, но не дату его смены — она доступна
только поштучным запросом на каждого, что дорого.

Поэтому дату фиксируем сами: синхронизация видит переход `working → fired`
и пишет запись в журнал статусов. Наша дата — дата, когда факт стал известен,
и для механик со сгоранием баллов она честнее чужой.

## Приветственный бонус

Начисляется после нескольких завершённых поездок, один раз за человека.
Идёт через журнал операций на общих основаниях — см. `points.md`.

## Что не переносим

Счётчик дней без поездок в старом проекте считал не дни без поездок, а дни
простоя самого бота: инкремент шёл по разнице с отметкой последней проверки,
а отметка двигалась каждый прогон. Значения в сотни дней у большинства
водителей — следы периодов, когда синхронизация не работала.

Такое поле нельзя показывать в интерфейсе и нельзя переносить как есть.

Тестовые аккаунты опознаются по пустому статусу работы — на четырёх таких
записях лежит 100 014 536 баллов. В новую схему не переносятся.
