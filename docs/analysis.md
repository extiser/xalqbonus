# Разбор: почему переписываем

Документ фиксирует, что было найдено в действующем боте и на каких цифрах основаны
решения. Это исторический документ — он описывает состояние на момент разбора
и не переписывается по мере развития проекта.

Полный разбор старого проекта — `../../xalqbonusbot/docs/`.

---

## 1. Зачем переписываем

Действующий бот работает и его данные — источник правды. Переписывание начато не ради
чистоты кода, а из-за двух конкретных проблем, которые в текущей архитектуре не чинятся
точечно.

### 1.1. Баллы теряются системно

`services/tripService.js` опрашивает Fleet API окном `[driver.last_checked, now]`
с фильтром по **`booked_at`** — времени бронирования заказа. Окно скользящее, без
перекрытия: после успешного прогона `last_checked` двигается на `now`.

Поездка, забронированная в 13:50 и завершённая в 14:20, при опросе в 14:00 попадает
в выборку со статусом `transporting`. Запись создаётся, балл не начисляется. На следующем
прогоне окно `[14:00, 15:00]` её уже не содержит — `booked_at` остался в прошлом.
Поездка не будет запрошена никогда.

Код это предусматривает — есть ветка «была незавершённой, теперь завершилась» — но она
недостижима, потому что окно построено по `booked_at` и повторно поездку не вернёт.

**Замер по продовому дампу от 15.08.2026** (1 162 756 строк в `Trips`):

| статус | строк | доля |
|---|---:|---:|
| `complete` | 556 534 | 47.9% |
| `cancelled` | 367 526 | 31.6% |
| `transporting` | 164 313 | 14.1% |
| `driving` | 55 801 | 4.8% |
| `waiting` | 16 563 | 1.4% |
| `none` | 2 019 | 0.2% |

Нижние четыре — **238 696 поездок (20.5%)**, зависших в промежуточном статусе.
Поездка не может остаться «в процессе перевозки» навсегда: она либо завершилась,
либо была отменена. Контрольный признак: **у всех 238 696 записей `ended_at` пустой**,
без единого исключения. Это ровно те поездки, которые были пойманы на лету и больше
никогда не перезапрашивались.

Затронуто **1 449 водителей из 4 062** — 36% парка. Если доля успешных среди зависших
та же, что в целом (60%), недоначислено порядка **140 000 баллов**.

Ошибка смещена строго в одну сторону: бот всегда показывает меньше фактического.
Отсюда постоянные расхождения с диспетчерской и претензии только в одну сторону.

**Измерено сверкой с Fleet API (28.08.2026), окно 20–27.08.** Прикидка «около 24%»
подтвердилась, но считать её надо по завершённым: недозаписано **24.4–24.8%
завершённых заказов** водителей программы. Доля по всем заказам ниже — 17.1–17.6%, —
потому что отменённые бот пишет почти полностью: из 2 714 зависших отменённых
по API он потерял 35. К баллам отношение имеет первое число.

Расхождение **одностороннее**: записей базы без пары в API нет ни одной. Бот теряет
заказы и задваивает записи, но не выдумывает поездок, которых не было.

Недостача состоит из двух вёдер разной природы, и это важнее самой доли:

| ведро | заказов | у скольких водителей | концентрация |
|---|---:|---|---|
| зависли без времени завершения | 2 714 | 251 из 273 | первая десятка держит 13.5% |
| не записаны вовсе | 475 | 43 | первая десятка держит 84.8% |

Первое — механизм этого раздела, ровный слой по всем. Второе — точечный отказ
опроса по конкретным водителям, и он возможен только потому, что состояние
синхронизации в старом боте лежит **на водителе**: у каждого свой `last_checked`,
и застрять может отдельный человек. Почему именно эти сорок три — не выяснялось.

Полностью — `_reference/analysis/legacy-vs-api-2026-08-27.md`, вместе с разделом
о том, чего эти числа не показывают.

### 1.2. Баланс не поддаётся аудиту

`Drivers.points` — одно число, которое инкрементят пять независимых мест: начисление
за поездки, приветственный бонус, списание при заказе, возврат при отмене, ручное
начисление рутом. Журнала операций нет. На вопрос «откуда у водителя 342 балла»
ответить нечем.

Побочный эффект — гонка между кроновыми задачами: `tripService` делает атомарный
`increment`, `bonusService` — `read-modify-write` по значению, прочитанному до начала
цикла. Начисления затираются.

**Наблюдение из дампа:** сумма баллов по всем водителям — 109 105 684, из них
**100 002 299 у одного водителя** (91.7% всех баллов системы). Разбор схемы
27.08.2026 подтвердил: это не водитель — `profile_id` длиной 31 символ,
в реестре парка отсутствует, `car_number = 'not_found'`, ноль поездок.
Похоже на тестовое начисление через `manualy_add_points`, истории нет.
Реальные обязательства парка без этой записи — около 9.1 млн баллов
на 4 061 водителя, в среднем 2 240 на человека.

### 1.3. Упор в лимит API

Опрос идёт **по каждому водителю отдельно**: 4 062 запроса в час при лимите 5 000.
`BATCH_SIZE` из-за ошибки в формуле вырождается в 1, пауза 500 мс перед каждым запросом —
полный обход занимает под час при часовом кроне. Система работает на пределе,
и уменьшить задержку начисления в этой схеме нельзя.

## 2. Ключевое техническое решение

Эндпоинт `/v1/parks/orders/list` **не требует** `driver_profile` в запросе и умеет
фильтровать по **`ended_at`**. Можно забирать все заказы парка сразу, пачками по 500.

```
query.park.id                    — только парк, без driver_profile
query.park.order.ended_at.from   — фильтр по времени ЗАВЕРШЕНИЯ
query.park.order.ended_at.to
limit: 500
```

Что это меняет:

- при ~1 900 поездках в сутки один запрос покрывает несколько часов работы парка;
  опрос раз в минуту стоит ~1 запрос вместо 4 062 в час — **примерно в 2 000 раз дешевле**;
- фильтр по `ended_at` устраняет причину потерь: поездка попадает в окно в момент
  завершения, а не бронирования. Попасть «в середину» больше невозможно;
- окно можно делать с перекрытием — дедуп по `trip_id` разберётся;
- задержка начисления падает с часа до минуты.

**Это допущение требует проверки на боевом API до начала работ.** Проверяем:
принимает ли эндпоинт запрос без `driver_profile`, возвращает ли каждый заказ
`driver_profile_id` (иначе неизвестно, кому начислять), работает ли пагинация
по `cursor` в этом режиме. Пока не проверено — весь план по синхронизации гипотеза.
Это Этап 1.

Старый обход по водителям не выбрасывается: он остаётся как медленная фоновая сверка
раз в сутки, а не как основной механизм.

## Проверка на свежих данных (дамп от 27.08.2026)

Диагноз подтверждён на дампе, снятом через двенадцать дней после первого разбора.
Механизм потери не остановился и работает ежедневно.

| | 15.08.2026 | 27.08.2026 |
|---|---:|---:|
| поездок всего | 1 162 756 | 1 194 538 |
| зависших в промежуточном статусе | 238 696 | 243 613 |
| доля зависших | 20.5% | 20.4% |
| затронуто водителей | 1 449 | 1 477 |
| оценка недоначисленного | ~140 000 | ~146 000 |

**Разделение по `ended_at` идеально чистое.** У всех 950 925 поездок в статусах
`complete` и `cancelled` время завершения заполнено. У всех 243 613 зависших —
пусто, без единого исключения. Совпадение на миллионе строк случайным не бывает:
это и есть подпись механизма.

**Ежедневный темп потерь.** По 400–470 поездок в сутки, устойчиво 15–16% дневного
объёма. В пересчёте на баллы — порядка 250 недоначисленных в день.

**Провалов в сборе три, а не один.** Май–июнь 2026 — 4 373 и 5 239 поездок
против 35 000–80 000 в соседних месяцах, и ни одной зависшей. Такой же провал
есть в мае 2025: 6 783 поездки, зависших ноль. Бот в эти периоды почти
не собирал данные.

Для перепроверки это значит, что три периода придётся восстанавливать целиком,
а не отдельными потерянными поездками, — и оценка недоначисленного к ним
неприменима, потому что считается от того, что записано.

**Пустая таблица `DriverPoints`.** Существует в схеме, содержит ноль строк.
Журнал операций когда-то задумывался и не был доведён.

## Отказы по лимиту: что это на самом деле (27.08.2026)

**Замер порога.** После полутора минут тишины проходит три запроса подряд,
четвёртый возвращает `429` с телом `Limit exceeded.` Заголовков `Retry-After`
и `X-RateLimit-*` Яндекс не присылает — обрабатывать приходится вслепую,
по коду ответа.

**Что в логах старого бота.** 241 277 записей «API вернуло 429. Пропуск водителя»
на 187 прогонов крона — около **1 290 пропущенных водителей за проход**, примерно
треть парка каждый час. По часам ровно: 1 100–1 500.

**Но потерей баллов это не является.** При отказе бот не двигает отметку последней
проверки, и в следующий час окно становится шире — пропущенные поездки попадают
в него. Это сделано намеренно и работает. Цена отказов не в потерянных баллах,
а в том, что система упёрлась в потолок: задержку начисления нельзя уменьшить,
проход нельзя ускорить, треть парка каждый час обслуживается с опозданием.

**Ошибочная гипотеза, зафиксирована чтобы не воскресала.** Мы предположили, что
отказы по лимиту и есть причина, по которой 2 472 водителя имеют баллы и ноль
поездок в базе. Проверка по когортам эту версию опровергла:

| когорта | всего | с баллами и без поездок | доля |
|---|---:|---:|---:|
| массовый импорт 18.12.2024 | 2 916 | 2 286 | 78.4% |
| зарегистрировались позже | 1 183 | 186 | 15.7% |

Балансы приехали **вместе с импортом из предыдущей системы**, а не были начислены
этим ботом. Поэтому оценка недоначисленного остаётся прежней — порядка 146 000
баллов, считанных от записанных поездок.

**Но это брутто, и встречная ошибка тоже есть.** `trip_id` в старой базе
не уникален: 59 812 лишних строк, и 4 877 пар `(trip_id, driver_id)` в статусе
`complete` записаны дважды. При курсе в один балл за поездку это 4 877 баллов,
начисленных повторно. Бот ошибается в обе стороны, и перед разговором с парком
про доначисление цифру надо считать нетто.

**Несостыковка разрешена.** Наш замер давал меньше запроса в секунду и упирался,
старый бот при этом устойчиво получал около 0.8 успешных запросов в секунду —
модели не сходились. Рабочее предположение «запрос по всему парку стоит дороже»
подтвердилось прямо: лимитер считает стоимость запроса, а не частоту, и глубокая
страница списка отбивается независимо от пауз. Разбор и замеры — `yandex-fleet.md`.

Это два разных ограничения, а не одно. Суточную квоту ключа старый бот
действительно выбирает под ноль. Наши отказы на выгрузке к ней отношения
не имели. Клиент API всё равно получает свой token bucket, экспоненциальный
backoff и circuit breaker, и не верит в то, что ключ принадлежит только ему.

## Размер парка против размера программы (27.08.2026)

**Первая версия этого раздела была неверной, и ошибка стоила бы направления
всей работы по лояльности.** Здесь стояло: в парке 25 389 водителей, в программе
4 099, то есть охват 16%, и рядом лежит нетронутый парк вшестеро больший —
значит дешевле приводить новых, чем растить активных.

Полная выгрузка заказов за неделю это опровергает.

| | Водителей |
|---|---:|
| профилей в реестре парка | 25 390 |
| из них со статусом `working` | 22 884 |
| **сделали хотя бы один заказ за неделю** | **430** |
| активных, помеченных `working` | 430 |
| `working` без единого заказа за неделю | 22 454 (98.1%) |

Работающих в парке не 22 884, а 430. Остальные числятся: `fired` проставлен
всего у 2 392 профилей из 25 390, статус после ухода человека не меняют.

Против этого — 4 099 когда-либо зарегистрированных в программе.

**Пересечение измерено 28.08.2026** сверкой с Fleet API по ключу `profile_id`,
и вторая версия этого раздела тоже оказалась неточной. Формулировка «программа
покрывает практически всех, кто реально ездит» неверна:

| | Водителей |
|---|---:|
| активных за неделю в парке | 430 |
| **из них есть в программе** | **279 (64.9%)** |
| нет в программе | 151 |
| участников программы, не сделавших ни одного заказа за неделю | 3 809 из 4 086 |

**Что это меняет в постановке.** Направлений три, и по размеру они разные:

- **151 активный водитель вне программы.** Направление «приводить тех, кто уже
  ездит» существует, вопреки прошлой версии раздела. Но по заказам оно легче,
  чем по головам: 35% активных против 26.8% заказов, медиана 26 заказов в неделю
  против 54 у участников. Отсутствие в базе — установленный факт, причина —
  нет: ни телефон, ни номер ВУ не находят ни одного из 151, при том что
  на контрольной группе те же поля находят 88–90%
- **3 809 участников программы, не ездивших за неделю.** Крупнее первого
  в двадцать пять раз по головам, но вернутся ли они за баллами — не проверял
  никто
- **279 активных участников** — рост частоты поездок у тех, кто уже внутри

«Активный» здесь — сделавший хотя бы один заказ за конкретную неделю 20–27.08.
Отпуск, ремонт и болезнь в это число не попали, сезонность одной недели не видна.

Оговорка про историю остаётся: 25 390 — все, кого парк знает с 2018 года.
