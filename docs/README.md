# docs — принципы проекта

## Что здесь есть

Общие принципы: как система устроена в целом, почему приняты те или иные решения,
что нельзя делать. Медленно меняющиеся вещи.

| Файл | О чём |
|---|---|
| `analysis.md` | разбор действующего бота: что найдено, на каких цифрах строятся решения |
| `principles.md` | слои, правило зависимостей, границы |
| `points.md` | принципы работы с баллами |
| `drivers.md` | принципы идентификации водителя |
| `miniapp.md` | принцип авторизации Mini App |
| `yandex-fleet.md` | справка по внешнему API (заполняется на этапе 1) |
| `decisions.md` | журнал решений: что решили, почему, что отвергли |
| `roadmap.md` | этапы, что чем блокируется |

## Чего здесь НЕ бывает

**Структур таблиц, полей, DDL.** Схема данных — это `prisma/schema.prisma`.
Документ, который её пересказывает, устаревает на первой же миграции
и начинает врать.

**Контрактов эндпоинтов.** Что принимает и возвращает ручка — видно в коде
обработчика и в zod-схеме рядом с ним.

**Описаний конкретных задач.** Задачу целиком описывает issue: что сделать,
как проверить, чего не делать. Issue одноразовый — сделали и закрыли.

**Того, что ещё не решено.** Документ не забегает вперёд. Если механика
не выбрана — она обсуждается в `../product/` или живёт в issue, но не оседает
здесь как будто уже принята.

## Почему так

Спецификация, которая описывает код, обречена: она уезжает вперёд реализации,
расходится с ней, и в какой-то момент никто уже не знает, чему верить.
Тогда её начинают «синхронизировать», и это становится отдельной работой,
которая ничего не производит.

Разделение простое:

```
docs/     принципы          меняются редко      источник истины
issue     задача            одноразовый         источник истины на время работы
код       реализация        меняется постоянно  документация того, как оно есть
```

Если возник вопрос «как устроена таблица X» — ответ в схеме, не здесь.
Если «почему мы вообще завели таблицу X» — ответ здесь.
