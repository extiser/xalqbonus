# XalqBonus — Инструкции для Claude Code CLI

## О проекте

Бонусная программа таксопарка Xalq Taxi (Узбекистан). Водители копят баллы за поездки
и меняют их на товары в офисах парка. Данные о поездках приходят из Yandex Fleet API.

Проект переписывается с нуля на базе разбора действующего бота. Старый код —
`../xalqbonusbot`, **только чтение**, менять его нельзя (кроме одного изменения,
оговорённого в roadmap: выключение крона).

## Стек

Nuxt 4 (Vue 3 + Composition API) поверх Nitro v2, TypeScript, PostgreSQL через Prisma,
BullMQ на Redis, Telegraf для бота. Интерфейсов два — Telegram Mini App и веб.
Инфраструктура — Docker и локально, и в проде, принципы в `docs/infra.md`.

Перечень пакетов с версиями и обоснованием — `docs/decisions.md`.

## Режим работы

- **Ведущий** — Руслан. **Исполняющий** — Claude.
- **Один issue = один чат CLI = одна ветка = один PR.**
- Продуктовые решения принимаются не здесь. Если задача упирается в продуктовый
  вопрос — остановиться и спросить, не решать самому.
- Post-MVP функциональность не реализуется, если не указана в issue явно.

## Получение задачи

Задачи живут на GitHub — `github.com/extiser/xalqbonus/issues`. Руслан даёт
номер issue, тело читается через `gh issue view {N}`. Тела хранятся также
в планировочной папке Руслана и туда же правятся: **issue на GitHub не
редактируется из CLI**, расхождение — повод остановиться и сообщить.

Тело issue содержит секции:

- **Задача** — что нужно сделать
- **Что прочитать** — принципы и участки кода, нужные для этой задачи
- **Что реализовать** — чеклист конкретных шагов
- **Критерий готовности** — как поймём что задача выполнена
- **Не делать** — что явно выходит за рамки

## Pre-flight check

**СТОП — не писать ни строчки кода, пока не пройдены все шаги.**

### Шаг 1 — Чтение (молча, без вывода в чат)

- [ ] Прочитан `docs/principles.md`?
- [ ] Прочитан весь текст issue (все 5 секций)?
- [ ] Прочитаны все файлы из секции «Что прочитать»?
- [ ] Понятно, что уже есть в коде по этой теме — посмотрел, а не предположил?
- [ ] Все пакеты, которые нужны, есть в `package.json` или названы в issue?
- [ ] Понятно как тестировать?

Если хотя бы один пункт «нет» — перейти к Шагу 3 и задать вопрос.

### Шаг 2 — Ветка (молча, обязательно до любых правок)

```bash
git checkout main
git pull
git checkout -b {type}/{N}-{slug}
```

`{N}` — номер issue на GitHub, `{type}` — тип из заголовка issue:
`feat`, `fix`, `chore`, `refactor`, `docs`, `research`.
Пример: `research/2-fleet-export`.

Ветка, issue и PR должны читаться вместе — без номера связь теряется
через неделю.

Каждую команду отдельно. Если любая упала — остановиться и сообщить на Шаге 3.

### Шаг 3 — Подтверждение или авто-старт

Вывести: чеклист pre-flight, название ветки, краткий план реализации.

Все пункты «да» и вопросов нет → «Pre-flight ok, начинаю реализацию» и старт
без отдельного подтверждения. Иначе — вывести вопросы и **ждать ответа**.

**Вопросы задаются только прозой, в тексте ответа. AskUserQuestion не
использовать никогда — ни одной вкладкой.** Несколько вопросов — нумерованным
списком, каждый с вариантами и явной рекомендацией.

Причина измерена: 28.08.2026 вопрос по задаче переноса был задан двумя вкладками,
вторая осталась непрочитанной — интерфейс показывает активной только первую.
Ответ ушёл, работа продолжилась, решение по второму вопросу было принято молча,
в задаче, необратимо пишущей балансы четырёх тысяч человек. Прозаический вопрос
пропустить нельзя: он лежит в ответе целиком, всеми частями сразу.

## Pull request

- **Title PR = заголовок issue дословно**, без префиксов. История PR и история
  issue должны читаться вместе
- В теле PR — строка `Closes #N`. Issue закрывается мержем, руками не трогается
- Один issue = одна ветка = один PR. Ветка от `main`, имя из шага 2
- **`--assignee extiser` обязателен** в каждом `gh pr create`. Автор проставляется
  токеном, исполнитель — нет, и без флага поле остаётся пустым; дописывать его
  руками после каждого PR — работа, которой не должно быть

## Соглашения по коду

- TypeScript везде, `any` **запрещён**
- Комментарии в коде — **на русском**. Переменные, функции, типы — **на английском**
- Компоненты: `PascalCase`, файлы `ComponentName.vue`
- Composables: `useEntityAction.ts`, store: `useEntityStore.ts`
- API routes: REST-стиль — `/api/drivers`, `/api/drivers/:id/points`
- Сокращения в именах запрещены: не `usr`, `cnt`, `res`, `tmp`, `i` — писать полностью

Подробности — `docs/principles.md`.

## Правило зависимостей

```
api → services → repositories → prisma
         |
         v
      adapters
```

- адаптер Yandex Fleet **не знает про базу**
- репозитории **не знают про Fleet**
- сервисы **не обращаются к Prisma напрямую**
- обработчики `api/` тонкие: разбор запроса, вызов сервиса, формат ответа

Нарушение этого правила — то, из-за чего в старом проекте `actions/` вызывали
контроллеры мимо сервисов, а `controllers/` оказались не контроллерами.

## Куда класть новое

- обработчик HTTP-ручки — `server/api/` (файловый роутинг Nitro)
- бизнес-логика — `server/services/{домен}/`, по файлу на операцию
- внешние системы — `server/adapters/`
- очереди и воркеры — `server/queues/`
- доступ к данным — `server/repositories/`
- схема и миграции — `prisma/`
- тесты — `tests/`
- принципы — `docs/` (**только чтение**)
- продуктовые обсуждения — `product/` (**только чтение**, правит Руслан)

## Работа с баллами

**Единственный способ изменить баланс водителя — запись в журнал `point_entries`.**

Прямое изменение баланса запрещено везде, кроме сервиса, который пишет журнал
и обновляет кэш в одной транзакции. Каждая операция обязана иметь ключ
идемпотентности по схеме из `docs/points.md`.

Если задача требует начислить или списать баллы и в спеке нет подходящего ключа —
остановиться и спросить. Не придумывать ключ самостоятельно.

## Где что описано

```
docs/     принципы          меняются редко      почему так устроено
issue     задача            одноразовый         что делать сейчас
код       реализация        меняется постоянно  как оно есть на самом деле
```

Структуры таблиц, поля, контракты ручек — **в issue**, не в `docs/`.
Схема данных документируется схемой Prisma, контракт ручки — её кодом
и схемой валидации рядом. Документ, пересказывающий код, устаревает
на первой миграции и начинает врать.

Если issue противоречит принципу из `docs/` — остановиться и спросить,
а не выбирать молча.

## Важные ограничения

- **Прод не трогаем.** Никаких подключений к боевой БД, никаких запросов к Fleet API
  на боевых ключах без явного разрешения в issue.
- **Старый проект `../xalqbonusbot` — только чтение.**
- **Наши таблицы живут в схеме `xb`.** Схема `public` принадлежит старому боту
  и **только читается** — писать в неё нельзя ничем и никогда.
- **`prisma db pull` не запускается.** Структуру старой базы мы не наследуем,
  схема ядра проектируется заново.
- **Тесты пишутся только на ядро начисления баллов.** Ручки, интерфейс и бот
  не покрываются — это решение, а не недоделка (`docs/infra.md`).
- `.env` не коммитить никогда. Проверять `git status` перед первым коммитом.
- Не выдумывать поля и таблицы, которых нет ни в схеме, ни в issue.
  Схема данных — `prisma/schema.prisma`, она же документация по структуре.
- Не изобретать продуктовое поведение. Нет в issue — вопрос Руслану.
- Не заводить документы «про запас» и не описывать в `docs/` то, что уже
  описано кодом. Документация кода — это код.

## Команды

**Единственная входная дверь — `Makefile`.** `docker compose` и `npx` руками
не набираются: у любой операции над стеком есть цель.

```bash
make help          # список целей с описаниями
make up-d          # поднять локальный стек (postgres:5434 + redis:6381)
make logs          # логи стека
make psql          # psql локальной базы
make migrate       # применить миграции
make typecheck
make test
```

Нужна новая операция — добавляется целью в `Makefile`, а не строкой в чат.
Источник истины по скриптам — `Makefile` и `package.json`.
