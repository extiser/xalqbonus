# 02 — Разведка Fleet API на живых данных

**Область:** integration
**Этап:** 1
**Статус:** ЗАКРЫТ 27.08.2026 — выполнен вручную, до issue 01, скриптами
`scripts/probe-fleet.py` и `scripts/probe-ratelimit.py`. Результаты
в `docs/yandex-fleet.md`, примеры ответов в `_reference/fleet-api/samples/`.

Все три обещания документации подтверждены на боевом API. Порог запросов замерен.
Задача для CLI не требуется — оставлена как запись о проделанном.

## Задача

Проверить на боевом API то, что обещает документация, и замерить то, чего
в документации нет. Задача разведочная: код синхронизации здесь не пишется,
пишется скрипт-зонд и заполняется отчёт.

Документация уже собрана локально — `_reference/fleet-api/`. Ходить на сайт
не нужно.

## Что прочитать

- `docs/yandex-fleet.md` — на что опираемся и чего не знаем
- `_reference/fleet-api/01-orders.md` — контракт списка заказов
- `_reference/fleet-api/00-general.md` — авторизация, форматы, коды ошибок

## Что проверить

Документация утверждает три вещи. Каждую подтвердить или опровергнуть на живом API.

- [ ] **Запрос без водителя.** `POST /v1/parks/orders/list` только с `query.park.id`,
      без `driver_profile`. Принимает или требует водителя?
- [ ] **Фильтр по времени завершения.** `query.park.order.ended_at.from/to`
      без `booked_at`. Работает? Попадают ли в выборку заказы, забронированные
      до начала окна и завершённые внутри него — это и есть весь смысл затеи
- [ ] **Идентификатор водителя в ответе.** Присутствует ли `driver_profile.id`
      в каждом заказе, включая отменённые и незавершённые
- [ ] **Пагинация курсором** в этом режиме: работает ли, стабилен ли курсор,
      как выглядит конец выборки

Чего в документации нет и что надо выяснить опытом:

- [ ] **Реальный порог запросов.** Аккуратно нащупать, при какой частоте приходит
      `429`. Начинать редко, наращивать плавно, при первом `429` остановиться
      и записать частоту. **Ключ боевой, парк живой — не устраивать нагрузочное
      тестирование**
- [ ] **Поведение после `429`:** через сколько отпускает, есть ли `Retry-After`,
      не блокируется ли ключ
- [ ] **Максимальная длина окна** по `ended_at`: принимает ли сутки, неделю, месяц
- [ ] **Глубина истории:** насколько далеко в прошлое отдаёт заказы —
      от этого зависит, что вообще можно восстановить перепроверкой
- [ ] **Часовой пояс:** что возвращается в `ended_at` и как соотносится
      с временем парка (Ташкент, UTC+5)
- [ ] **Реальный объём:** сколько заказов в сутки у парка по факту

## Что реализовать

- [ ] Адаптер-заготовка клиента Fleet API в `server/adapters/yandex-fleet/`:
      заголовки, базовый URL, разбор ответа, типы. Без бизнес-логики
- [ ] Скрипт-зонд, запускаемый вручную, который делает перечисленные проверки
      и печатает результат
- [ ] Заполнить `docs/yandex-fleet.md` разделом «Проверено на живом API»:
      что подтвердилось, что нет, найденные пороги и ограничения
- [ ] Сохранить реальный пример ответа в `_reference/fleet-api/samples/`
      **с вычищенными персональными данными пассажиров** — в ответе есть
      `park_details.passenger.name` и телефоны

## Критерий готовности

В `docs/yandex-fleet.md` есть раздел «Проверено на живом API» с ответом по каждому
пункту выше и конкретными числами там, где они замерены. Лежит очищенный пример
реального ответа.

Если хотя бы одно из трёх обещаний документации не подтвердилось — **остановиться
и сообщить Руслану**, не придумывая обходной путь. Схема синхронизации в этом случае
пересматривается целиком, и это продуктовое решение.

## Не делать

- Не писать воркер, очередь и логику начисления — это следующие задачи
- Не создавать таблиц и миграций
- Не писать ничего в боевой Fleet API. Только чтение: никаких транзакций,
  никаких изменений профилей
- Не устраивать нагрузочное тестирование боевого ключа
- Не сохранять персональные данные пассажиров в репозиторий
