# 01 — Окружение проекта

**Область:** infra
**Этап:** 0
**Блокируется:** ничем

## Задача

Поднять рабочее окружение по образцу OmniBox: каталог `docker/`, Makefile как
единственная входная дверь, локальный стек из приложения, воркера, PostgreSQL
и Redis. Восстановить продовый дамп в схему `public`, завести пустую схему `xb`
под наши будущие таблицы.

**Схему данных в этой задаче не проектировать.** Prisma подключается и настраивается,
но моделей в ней нет ни одной. Структура ядра обсуждается с Русланом отдельно.

## Что прочитать

- `CLAUDE.md`
- `docs/infra.md` — принципы инфраструктуры, читать целиком
- `docs/decisions.md` — стек и версии
- `../omnibox/docker/` и `../omnibox/Makefile` — образец, с которого снимаем структуру

Образец не копировать дословно: в OmniBox есть Telegram-адаптеры, файловое
хранилище, тестовый стек и три окружения, которых у нас нет. Берём форму,
а не содержимое.

## Что реализовать

- [ ] Каталог `docker/`: `Dockerfile`, `compose.local.yml`, `compose.server.yml`,
      `compose.prod.yml`, `compose.proxy.yml` (Caddy)
- [ ] Удалить `docker-compose.yml` из корня — его заменяет каталог
- [ ] `Dockerfile` в три этапа по образцу OmniBox: `build` → `migrate-tools` → `runner`.
      В финальный образ едет только Prisma CLI нужной версии, а не весь `devDependencies`
- [ ] `Makefile` с целями: `help`, `up`, `up-d`, `down`, `restart`, `logs`, `ps`,
      `shell`, `psql`, `migrate`, `migrate-create`, `typecheck`, `test`,
      плюс набор `prod-*`. Каждая цель с `##`-описанием, `make help` печатает список
- [ ] Локальный стек: `app`, `worker`, `postgres` (5434), `redis` (6381).
      `app` и `worker` собираются из одного образа и отличаются только командой запуска
- [ ] Healthcheck PostgreSQL **по TCP, а не по unix-сокету**: на первом старте
      контейнера initdb поднимает временный сервер, слушающий только сокет,
      и проба по сокету зеленеет до того, как база готова принимать соединения
- [ ] Ручки `/api/health` (процесс жив) и `/api/ready` (база и очередь доступны) —
      healthcheck образа бьёт в первую, выкат ждёт вторую
- [ ] Nuxt 4 поверх существующего дерева, не ломая `docs/`, `issues/`, `_backup/`
- [ ] Установить зависимости из `docs/decisions.md`, **точные версии дописать туда же**
- [ ] Восстановить `_backup/xalqbonus-2026-08-27-1247.dump` в локальную базу,
      в схему `public`, как есть. Формат custom, восстанавливать `pg_restore`
      внутри контейнера с `--no-owner --no-privileges`
- [ ] Создать пустую схему `xb`
- [ ] Prisma: `schemas = ["public", "xb"]`. Моделей не описывать, миграций не создавать
- [ ] Vitest настроен, `make test` отрабатывает (тестов пока нет — важно, что команда живёт)
- [ ] Проверить `.gitignore`: `_backup/` и `*.dump` на месте, дамп не в индексе

## Критерий готовности

На чистой машине: `cp .env.example .env` → `make up-d` → восстановление дампа.

- `make ps` показывает четыре здоровых контейнера
- `/api/health` и `/api/ready` отвечают
- `make psql` пускает в базу
- в базе схема `public` содержит восстановленные таблицы старого бота,
  схема `xb` существует и пуста
- `make typecheck` и `make test` отрабатывают без ошибок
- `make help` печатает список целей с описаниями

Контрольная цифра по дампу: он снят 27.08.2026, поэтому числа строк **не совпадут**
с замерами из `analysis.md` — те сделаны по дампу от 15.08. Расхождение ожидаемо,
это не признак неудачного восстановления.

## Не делать

- **Не проектировать схему данных.** Ни одной модели Prisma, ни одной миграции
  с таблицами. Это отдельная задача, структура обсуждается с Русланом
- **Не запускать `prisma db pull`.** Структуру старой базы мы не наследуем
- **Не писать в схему `public`.** Она только читается
- Не писать бизнес-логику
- Не подключаться к боевой БД и боевому Fleet API
- Не трогать `../xalqbonusbot` ничем, кроме чтения
- Не заводить dev-окружение — только `local` и `prod`
- Не добавлять команд в чат вместо целей Makefile
